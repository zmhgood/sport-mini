# 成员、家庭、目标与统计口径草案

2026-10-13；依据当前三个仓库代码。用户已确认：离开成员的个人/家庭历史都保留、当前权限立即撤销；全部完成一个目标动作计一次。其他标注为草案的指标仍待确定，不代表这些指标已经实现。

## 数据关系与约束

| 实体 | 标识/关系 | 必须检查的约束 |
| --- | --- | --- |
| 用户 users | 用户 ID；OpenID 对应微信身份 | 一人一个账户；昵称是展示字段，不能充当身份键 |
| 家庭 families | creator_id 是创建者 | 创建者与当前管理员分别记录；删除家庭使邀请码和当前访问失效 |
| 家庭成员 family_members | family_id + user_id | 同一家庭只有一个有效成员关系；支持软删除后再加入；成员加入多个家庭不产生多个用户 |
| 目标 daily_goals | family_id | 目标所属家庭固定；启停与删除是不同状态 |
| 目标参与者 goal_members | goal_id + user_id | 是家庭成员的子集；家庭成员不等于已经参与所有目标 |
| 目标动作 goal_exercises | ID + goal_id + exercise_id | 同一动作模板可被不同目标引用；目标动作 ID 与动作模板 ID 不可混用 |
| 每日进度 goal_completions | goal_member_id + goal_exercise_id + date | 两个关联必须属于同一目标；建议唯一；completed_sets 是当天绝对值，不是每次追加量 |
| 锻炼流水 user_exercise_records | 新写入 completion_id 关联每日进度；旧行为 NULL | 新关联绝对值更新，旧流水保留；统计从 canonical 每日进度读取，不能用请求次数累计 |
| 日汇总 user_daily_stats | user_id + date | 是派生数据；必须可与明细对账，不能用按钮点击次数累计 |

角色矩阵必须覆盖：游客、普通成员、目标参与者、家庭管理员、被移除/退出成员、其他家庭成员、平台 admin。平台 admin JWT 与微信用户 JWT 是不同权限身份；家庭管理员不能操作平台管理接口。

## 建议指标定义

下列规则分为基础约束与待确认的业务口径。不得根据当前实现的返回值反推正确答案。

| 指标 | 建议口径/公式 | 确认状态 |
| --- | --- | --- |
| 当前家庭成员数 | 当前有效 family_members 去重计数；排除软删除成员 | 基础约束 |
| 平台用户数 | 有效用户 ID 去重；一个用户属于两个家庭仍算一个人 | 基础约束 |
| 家庭创建者 | families.creator_id；转移管理员不改变创建者 | 字段含义已明确 |
| 当前管理员 | 当前有效成员中 role=admin；转移后恰好一人 | 建议约束；当前接口缺少完整保证 |
| 目标参与人数 | 该目标有效参与者数，不直接使用家庭总人数 | 基础约束；离开成员展示另行确定 |
| 完成组数 | 合法关联的每日进度绝对值求和；0 ≤ completed_sets ≤ target_sets | 基础约束 |
| 完成动作数/锻炼次数 | 同一用户、日期、目标动作，全部完成计 1；重复写入不增加 | 用户已确认 |
| 完成目标数 | 当天该用户该目标所有要求动作完成，计 1 | 建议口径 |
| 用户目标进度 | SUM(completed_sets) / SUM(target_sets)；与“动作完成率”分别命名 | 建议口径；分母 0 时显示暂无计划，不显示 100% |
| 动作完成率 | 已全部完成的目标动作数 / 要求动作数 | 建议口径，不能与组数进度混用 |
| 家庭目标总进度 | 所有计入参与者的完成组数 / 所有计入参与者的要求组数 | 待确认：是否采用此聚合；不平均不同分母的百分比 |
| 锻炼天数 | 有 completed_sets > 0 的业务日期去重 | 建议口径；多家庭同日只计一天 |
| 时长 | 优先真实计时；当前无真实计时，建议统一显示“估算时长”，以秒汇总后转分钟 | 每组估算秒数待确认；示例暂用当前总统计的 30 秒/组，不视为医学或产品结论 |
| 热量 | 尚未计算时显示暂不支持，不能把固定 0 当测量结果 | 当前实现限制 |
| 周/月汇总 | 先明确业务时区、周期边界、明细主键与过滤范围，再汇总 | 建议 Asia/Shanghai；当前服务器 time.Now() 依赖运行时区 |
| 退出/移除后历史 | 个人历史保留；家庭历史保留并标记已离开；当前权限立即撤销 | 用户已确认 |
| 历史分母 | 历史当日的目标配置/参与者快照，避免后续计划修改改变历史完成率 | 待确认；当前数据模型没有完整快照支持 |

不是所有数字都应相等：平台今日流水数、全部完成动作数、组数和锻炼人数是不同指标。界面文案要说明其含义。部分完成可以计入组数和参与人数，但不能计入已确认的“锻炼次数”或把动作标记为全部完成。

## 可手算的固定对账数据

仅使用独立本地测试库内的合成数据；不覆盖现有用户、家庭和线上记录。

- U1 属于 F1、F2；U2 只属于 F1；U3 只属于 F2。F1、F2 当前成员数各为 2，平台唯一用户数为 3，而非 4。
- F1 的 G1 有 X1：3 组 × 10 次，X2：2 组 × 5 次；U1、U2 都参与。
- F2 的 G2 有 X3：1 组 × 10 次；X3 与 X1 引用同一动作模板，但目标动作 ID 不同；U1 参与。
- D1 当天 U1 在 G1 完成 X1=1、X2=1；U2 在 G1 完成 X1=3、X2=0；G2 尚无进度。

| 检查点 | 期望（按建议草案） |
| --- | --- |
| U1 G1 组数进度 | 2/5=40% |
| U1 G1 全部完成动作数、目标数 | 0、0；不能因两条部分进度显示 100% |
| U1 D1 组数、锻炼天数、估算分钟 | 2、1、floor((1+1)×30/60)=1；逐条取整会错误得到 0 |
| U2 G1 组数进度、动作完成率 | 3/5=60%、1/2=50%，分别命名 |
| F1 G1 总进度 | (2+3)/(5+5)=50%，按拟定聚合口径 |
| U1 将 X1 更新到 3、X2 更新到 2 | 绝对组数合计 5，而非 2+5=7；完成动作 2、目标 1；时长按统一单位汇总 |
| 完全相同请求串行 3 次、并发 10 次、响应丢失后重试 | 所有明细、日汇总、周汇总、admin 计数与首次成功一致 |
| U1 再完成 G2 X3=1 | 个人组数为 6、天数仍 1；两家庭各只统计自己的目标；相同模板不造成目标动作主键冲突 |
| 退出后旧 URL/旧 Token 提交 | 拒绝，不产生新明细；历史按已确认的保留规则处理 |
| D1→D2、周日→周一 | 新日进度从 0 开始；D1 历史保存；同一业务时区下归属唯一日期 |

## 已发现的实现差异

1. `service/goal.go:400` 的锻炼流水按 reps × completed_sets × 30 秒估算；`repository/user.go:95`、`service/user.go:168` 仅按 completed_sets × 30 秒。相同三组十次分别得到 900 秒与 90 秒。
2. `service/user.go:326` 逐条进行整数分钟换算；总统计是先汇总秒数再转换。这两种算法在两条各一组时得到 0 与 1 分钟。
3. 历史聚合按“存在动作记录”增加 CompletedNum，未检查是否达到目标组数；0 组记录也可能被计入。`service/user.go:155–170`。
4. `repository/user.go:79–101` 的总统计读取原始联表，没有一致的软删除/零进度过滤；`GetUserGoalTotalSets` 则排除被删除目标和目标动作，但未核验当前家庭成员资格，也未过滤 is_active。
5. 周统计对所有历史日期使用当前计划总组数，新增/修改目标可能改变旧周分母。`service/user.go:294–312`。
6. admin 用户统计实际上读取同一 `GetUserTotalStats`，不是流水表；平台概览今日记录数读取流水表。因此重复提交可能使概览增加、个人次数保持，产生对账差异。
7. 前端请求 `/user/statistics/by-family`，当前路由未注册；家庭统计不能据此判定为真实空数据。

这些是代码证据；实际数据库影响与跨端表现仍需按测试用例跑集成对账。本轮没有执行任何线上写入。
